# 요구사항 정의서

| 항목 | 내용 |
|---|---|
| 시스템 | 구매요청·전자결재 시스템 (purchase-approval) |
| 작성일 | 2026-11-23 |
| 버전 | 1.0 |

## 1. 개요

사내 구매는 지금까지 메일과 엑셀로 요청하고 결재를 받아 왔다고 가정합니다. 이 때문에

- 누가 어디까지 결재했는지 알 수 없고,
- 같은 문서를 두 사람이 동시에 처리하는 일이 생기며,
- 월별 부서 구매액을 매번 손으로 집계해야 합니다.

이 시스템은 **구매요청 → 전자결재 → 발주 → 입고·재고 반영**을 한곳에서 처리하고, 결재 이력과 변경 이력을 남깁니다.

## 2. 사용자와 권한

| 역할 | 코드 | 할 수 있는 일 |
|---|---|---|
| 직원 | `EMPLOYEE` | 구매요청서 작성·임시저장·상신·회수, 내 요청 조회 |
| 팀장 | `TEAM_LEADER` | 직원 기능 + 소속 팀 요청 결재 |
| 부서장 | `DEPT_HEAD` | 직원 기능 + 하위 팀 요청 결재 |
| 구매팀 | `PURCHASING` | 직원 기능 + 고액 요청 결재(구매팀장), 발주 등록, 입고 처리, 거래처·품목 관리 |
| 관리자 | `ADMIN` | 사용자·부서·직급·공통코드·메뉴 권한 관리, 감사·에러 로그 조회 |

- 한 사람은 역할 하나를 가집니다. 구매팀장은 `PURCHASING` 역할이면서 구매팀의 팀장입니다(직급 기준).
- 결재자는 사람을 직접 고르지 않고 **조직도에서 자동으로 정합니다**(4장 업무 규칙).

## 4. 업무 규칙

**BR-01 결재선.** 상신할 때 아래 순서로 만듭니다.
1. 기안자 소속 팀의 팀장 (`TEAM_LEADER`)
2. 그 팀의 상위 부서(본부)의 부서장 (`DEPT_HEAD`)
3. 합계 **5,000,000원 이상**이면 구매팀 팀장(`PURCHASING` 중 직급 서열이 가장 높은 사람)

기안자 본인이 결재자에 해당하면 그 단계는 건너뜁니다(예: 팀장이 직접 올린 요청). 결재자를 찾지 못하면 상신할 수 없습니다.

**BR-02 결재 순서.** 결재선은 앞 단계부터 하나씩 처리합니다. 지금 차례(`PENDING`)가 아닌 결재자는 처리할 수 없습니다.

**BR-03 반려.** 한 단계라도 반려하면 문서는 `REJECTED`가 되고 남은 단계는 처리되지 않습니다. 반려된 문서는 복사해서 다시 작성합니다.

**BR-04 회수.** 첫 결재자가 처리하기 전(`IN_APPROVAL`이고 1단계가 `PENDING`)일 때만 회수할 수 있고, 회수하면 `DRAFT`로 돌아갑니다.

**BR-05 수정 제한.** `DRAFT` 상태에서만 수정·삭제할 수 있습니다.

**BR-06 동시 처리.** 같은 문서를 거의 동시에 두 번 승인하면 한 번만 반영되고, 나중 요청은 "다른 사용자가 먼저 처리했습니다"를 보여 줍니다.

**BR-07 금액.** 품목 금액 = 수량 × 단가, 합계 = 품목 금액의 합. 금액은 서버에서 다시 계산하고 화면 값은 믿지 않습니다.

**BR-08 재고.** 입고 처리 때 재고를 늘리고 이력을 남깁니다. 재고는 음수가 될 수 없습니다. 동시에 입고해도 수량이 어긋나면 안 됩니다.

**BR-09 거래처 상태.** 휴업·폐업 거래처는 새 요청서에서 고를 수 없습니다. 상태 확인 API가 실패하면 "확인 안 됨"으로 저장합니다.

## 5. 비기능 요구사항

| ID | 항목 | 내용 |
|---|---|---|
| NFR-01 | 보안 | 비밀번호 BCrypt, CSRF 보호, 권한 없는 URL은 403 |
| NFR-02 | 이력 | 모든 테이블에 생성·수정 시각과 사용자 기록 |
| NFR-03 | 성능 | 목록 조회는 페이지당 쿼리 수가 데이터 건수에 비례해 늘지 않을 것(N+1 금지) |
| NFR-04 | 테스트 | 업무 규칙(BR)마다 테스트 코드, GitHub Actions에서 자동 실행 |
| NFR-05 | 배포 | Docker 이미지로 AWS EC2에 배포 |
| NFR-06 | 설정 | 비밀번호와 API 키는 환경변수로만 받음 |
