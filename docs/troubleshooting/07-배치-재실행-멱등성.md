# 같은 달 통계를 다시 집계하면: "이미 완료" 거절, 그다음엔 UNIQUE 위반

- 단계: 9단계 (Spring Batch 월별 통계, 결재 지연 알림) / 관련 PR: #9
- 키워드: Spring Batch JobInstance, JobParameters, 멱등성(idempotency), upsert, tasklet 트랜잭션, `Existing transaction detected in JobRepository`

## 상황

매일 02:00에 배치가 "부서별로 그 달에 최종 승인된 요청서 건수·금액"을 `monthly_purchase_stat`에 집계한다.
통계 화면에는 구매팀이 한 달을 골라 바로 다시 집계하는 [다시 집계] 버튼을 두었다. 승인이 늦게 처리됐거나 어젯밤 배치가 실패했을 때 쓰는 버튼이다.

처음 만든 것:
- job 파라미터: `yearMonth` 하나 (`2026-11`)
- writer: 집계한 줄을 그대로 `save(new MonthlyPurchaseStat(...))`

## 증상 1: 두 번째 클릭은 실행조차 안 된다 (`NightlyBatchTest` [문제1])

```
JobInstanceAlreadyCompleteException:
  A job instance already exists and is complete for identifying parameters={'yearMonth':'{value=2026-11, ...}'}.
  If you want to run this job again, change the parameters.
```

## 원인 1

Spring Batch는 **job 이름 + 식별 파라미터 = JobInstance 하나**로 본다. 실행 이력을 `BATCH_JOB_INSTANCE`, `BATCH_JOB_EXECUTION` 테이블에 남기고,
이미 COMPLETED인 인스턴스를 같은 파라미터로 다시 실행하면 거절한다. "같은 일을 실수로 두 번 하지 않게" 하려는 안전장치다.
(실패(FAILED)한 인스턴스는 같은 파라미터로 다시 실행하면 이어서 하는 **재시작**이 된다.)

## 증상 2: 파라미터를 바꿔 다시 돌리면 이번엔 step이 FAILED (`NightlyBatchTest` [문제2])

누를 때마다 다른 인스턴스가 되도록 `requestedAt`(누른 시각)을 파라미터에 넣었다. 실행은 됐지만 step이 실패했다.

```
DataIntegrityViolationException: could not execute statement
  ... Unique index or primary key violation: "public.uk_monthly_stat_month_dept_INDEX_2 ON public.monthly_purchase_stat(stat_month ..., department_id ...)"   (테스트 H2 기준)
```

`UNIQUE(stat_month, department_id)`가 없었다면 실패하지 않고 **같은 달·같은 부서 줄이 두 개** 생겨서, 대시보드 금액이 조용히 두 배가 됐을 것이다. 더 나쁜 경우다.

## 원인 2

writer가 "있으면 고치고 없으면 넣기"가 아니라 "무조건 넣기"였다. 배치는 **다시 돌 수 있다고 가정하고** 만들어야 하는데(재시작, 수동 재실행, 두 서버의 스케줄러), 한 번만 돈다고 가정했다.

## 해결

### 1) writer를 upsert로: 몇 번 돌려도 결과가 같게 (멱등)

```java
statRepository.findByStatMonthAndDepartmentId(statMonth, row.departmentId())
        .ifPresentOrElse(
                stat -> stat.replace(count, row.totalAmount(), now),   // 더하지 않고 "새로 센 값으로 교체"
                () -> statRepository.save(new MonthlyPurchaseStat(...)));
```

`replace`가 핵심이다. `count += n`처럼 더하면 upsert라도 두 번 돌리면 두 배가 된다. 집계는 매번 원본(요청서)에서 처음부터 세고, 결과로 덮어쓴다.
UNIQUE 제약은 그대로 둔다: 앱 코드가 실수해도 DB가 마지막에 막는다.

### 2) 파라미터를 "몇 번 돌아도 되는가"에 맞춰 설계

| job | 식별 파라미터 | 의미 |
|---|---|---|
| `nightlyJob` (스케줄러) | `yearMonth` + `runDate`(날짜) | **하루에 한 번만.** 스케줄이 두 번 울리거나 서버가 두 대여도 두 번째는 "이미 완료"로 거절. 실패했으면 같은 날 다시 실행 = 재시작 |
| `monthlyStatJob` ([다시 집계]) | `yearMonth` + `requestedAt`(누른 시각) | **누를 때마다 새로.** 대신 writer가 upsert라 결과는 같다 |

`NightlyBatchTest` [해결]: 다시 집계를 두 번 → 줄 1개 그대로, 그 사이 승인 1건이 추가되면 세 번째 집계에서 2건으로 바뀐다.
실제 앱에서도 매분 돌게 cron을 바꿔 확인했다: 첫 실행은 COMPLETED, 다음 분 실행은 `야간 배치 실행 실패: A job instance already exists and is complete ...` 로그만 남고 넘어간다.

### 3) 알림도 같은 원리: dedupKey

결재 지연 알림(3일 넘게 대기)은 `notification.dedup_key = "APPROVAL_DELAY:{결재선 id}"` (UNIQUE)로 같은 결재 단계에 한 번만 만든다.
배치를 몇 번 돌려도 결재자에게 같은 알림이 쌓이지 않는다.

## 해결하다 또 막힌 것

1. **테스트에 `@Transactional`을 붙이면 job이 시작조차 안 된다.**
   ```
   IllegalStateException: Existing transaction detected in JobRepository.
   Please fix this and try again (e.g. remove @Transactional annotations from client).
   ```
   배치는 chunk마다 직접 커밋해야 하므로, 이미 열린 트랜잭션 안에서 시작하는 것을 막는다. 그래서 배치 테스트는 `@Transactional` 없이 데이터를 실제로 커밋하고 `DbCleaner`로 지운다.
   같은 이유로 job을 실행하는 `BatchRunner`, 시작할 때 집계하는 `StatsInitializer`에도 `@Transactional`을 붙이지 않았다. (`NightlyBatchTest` [막힌 것]이 이 예외를 재현한다.)
2. **tasklet도 트랜잭션 안에서 돈다 → 8단계 문제(트러블슈팅 06)가 배치에서 다시 생긴다.**
   매일 밤 거래처 상태 갱신 step은 국세청 API를 부른다. tasklet에 JPA 트랜잭션 매니저를 주면 API를 기다리는 내내 DB 커넥션을 붙잡는다.
   `VendorStatusStepTest`가 가짜 국세청이 불리는 순간 "이 스레드에 DB 커넥션이 묶여 있나"를 기록한다: JPA 트랜잭션 매니저 → `true`, `ResourcelessTransactionManager` → `false`.
   그래서 그 step만 DB 일을 안 하는 `ResourcelessTransactionManager`를 주고, 저장은 `VendorService.applyStatus`의 짧은 트랜잭션이 한다.
3. **테스트(H2)는 되는데 MySQL에서는 BATCH_ 테이블이 없다.** `spring.batch.jdbc.initialize-schema`의 기본값 `embedded`는 내장 DB에서만 테이블을 만든다. `always`로 바꿨다.
   이미 테이블이 있으면 Boot가 CREATE 오류를 무시하고 넘어가므로(`continueOnError`) 재시작해도 괜찮다.
4. **`@EnableBatchProcessing`은 붙이지 않는다.** Spring Boot 3(Batch 5)에서는 이걸 붙이면 Boot의 배치 자동 설정이 꺼져 위의 `spring.batch.*` 설정이 무시된다. 옛 블로그 예제에는 대부분 붙어 있어서 헷갈렸다.

## 전후 비교

| 상황 | 처음 (`yearMonth`만 + insert) | 지금 |
|---|---|---|
| 같은 달 [다시 집계] 두 번째 | `JobInstanceAlreadyCompleteException` | 실행됨, 줄 1개 그대로 |
| 파라미터만 바꿔 다시 실행 | UNIQUE 위반으로 step FAILED (UNIQUE가 없으면 금액 두 배) | upsert로 같은 결과 |
| 같은 날 야간 배치가 두 번 울림 | (해당 없음) | 두 번째는 거절, 로그만 |
| 3일 넘은 결재 알림을 다시 돌림 | (해당 없음) | dedupKey로 1건 유지 |

## 배운 점

- 배치는 "다시 돌 수 있다"가 기본 가정이다. 결과를 더하지 말고 교체(upsert)해서 멱등하게 만든다.
- JobParameters는 단순한 입력값이 아니라 "이 실행이 몇 번 허용되는가"를 정하는 설계다.
- 트랜잭션 범위 원칙(그 안에는 DB 일만)은 배치의 tasklet에도 그대로 적용된다.
