# 감사 로그: 실패 기록은 롤백으로 사라지고, 커밋에 실패한 승인은 "성공"으로 남았다

- 단계: 10단계 (AOP 감사 로그, 에러 로그) / 관련 PR: #10
- 키워드: Spring AOP, `@Around`, 어드바이스 순서(`@Order`), 트랜잭션 전파 `REQUIRES_NEW`, `TransactionSynchronization.afterCompletion`, 프록시와 self-invocation

## 상황

등록·수정·삭제·결재를 누가 언제 했는지 `audit_log`에 남긴다 (OPS-01). 서비스마다 기록 코드를 넣지 않고 어노테이션 한 줄로:

```java
@Audited(action = AuditAction.APPROVE, target = "구매요청서", id = "#requestId")
public void approve(Long requestId, LoginUser user, String comment) { ... }
```

처음 만든 `AuditAspect`:
- `@Order` 없음
- `proceed()` 뒤에 `auditLogRepository.save(...)` (업무와 같은 트랜잭션), 예외면 실패로 저장

## 증상 1: 실패 기록이 남지 않는다 (`AuditAspectTest` [문제1])

남의 차례인 문서를 승인하려는 시도(`NOT_YOUR_TURN`)는 감사 대상인데, 기록이 0건이었다.
업무 트랜잭션 안에서 실패 기록을 저장한 직후 예외가 올라가면, 트랜잭션 전체가 롤백되면서 **방금 쓴 실패 기록도 같이 롤백**된다.

## 증상 2: 커밋에 실패한 승인이 "성공"으로 남는다 (`AuditAspectTest` [문제2→해결])

같은 팀장이 두 탭에서 같은 문서를 승인하면, 늦게 커밋하는 쪽은 낙관적 락 충돌로 실패한다 (트러블슈팅 04).
그런데 이 충돌은 **메서드가 끝난 뒤 커밋할 때** 난다. 메서드는 예외 없이 돌아왔으니 aspect는 "성공"을 써 버렸다.

```
audit_log:  devlead APPROVE 구매요청서#5 성공   ← 실제로는 반영 안 됨
            devlead APPROVE 구매요청서#5 성공
```

감사 로그가 사실과 다르면 감사 로그로서 의미가 없다.

## 원인

1. `save()`가 업무 트랜잭션에 **참여(REQUIRED)**했다. 기록의 운명이 업무의 운명과 같아졌다.
2. aspect와 `@Transactional` 프록시 중 **누가 바깥인지 정하지 않았다**. aspect가 트랜잭션 안쪽이면 `proceed()`가 돌아온 시점은 아직 커밋 전이다.
   더구나 호출한 쪽이 더 큰 트랜잭션을 열어 두었다면(다른 서비스, 배치, 테스트) aspect가 바깥이어도 커밋 전이다.

## 해결

```java
@Aspect @Component @Order(1)      // 트랜잭션 어드바이스(LOWEST_PRECEDENCE)보다 바깥
public class AuditAspect {
    @Around("@annotation(audited)")
    public Object around(ProceedingJoinPoint pjp, Audited audited) throws Throwable {
        try {
            result = pjp.proceed();                       // 서비스 트랜잭션은 여기서 커밋까지 끝난다 (커밋 실패도 예외로 옴)
        } catch (Throwable e) {
            save(실패, e.getMessage()); throw e;
        }
        if (TransactionSynchronizationManager.isSynchronizationActive()) {   // 바깥에 트랜잭션이 아직 열려 있으면
            registerSynchronization(new TransactionSynchronization() {
                public void afterCompletion(int status) { save(status == STATUS_COMMITTED ? 성공 : 실패); }
            });
        } else {
            save(성공);
        }
        return result;
    }
}

@Transactional(propagation = Propagation.REQUIRES_NEW)   // AuditLogWriter.write
public void write(AuditLog log) { ... }
```

1. **저장은 항상 새 트랜잭션(REQUIRES_NEW).** 업무가 롤백돼도 기록은 따로 커밋된다. `afterCompletion` 안에서 DB에 쓸 때도 스프링 문서가 REQUIRES_NEW를 쓰라고 한다 (원래 트랜잭션은 이미 끝났지만 자원이 아직 묶여 있을 수 있어서).
2. **"성공"은 커밋이 확정된 뒤에 쓴다.** aspect를 트랜잭션 바깥에 두고, 그래도 바깥 트랜잭션이 있으면 끝날 때 결과를 보고 쓴다.
3. 감사 로그 저장이 실패해도 업무는 막지 않는다 (try/catch 후 ERROR 로그).

결과 (같은 두 탭 시나리오):

```
devlead APPROVE 구매요청서#5 성공
devlead APPROVE 구매요청서#5 실패  "트랜잭션이 커밋되지 않았습니다 (롤백)"
```

## 해결하다 또 막힌 것

1. **`@Order(Ordered.HIGHEST_PRECEDENCE)`로 두었더니 모든 @Audited 메서드가 터졌다.**
   ```
   IllegalStateException: Required to bind 2 arguments, but only bound 1 (JoinPointMatch was NOT bound in invocation)
   ```
   `around(ProceedingJoinPoint pjp, Audited audited)`처럼 어노테이션을 파라미터로 받으려면, 스프링이 맨 앞에 끼우는 `ExposeInvocationInterceptor`가 먼저 돌아야 한다.
   가장 높은 우선순위를 주면 그보다 앞에 서게 되어 바인딩을 못 한다. "트랜잭션보다 바깥"이면 충분하므로 `@Order(1)`로 바꿨다.
2. **같은 클래스 안에서 부르면 기록이 안 된다 (self-invocation).** `outer()`가 `this.inner()`를 부르면 프록시를 거치지 않아 `@Audited`도 `@Transactional`도 동작하지 않는다.
   테스트(`[함정]`)로 확인해 두고, 감사 대상은 컨트롤러가 직접 부르는 바깥 메서드에만 붙였다.
3. **`/requests/abc`가 500 + 에러 로그.** 화면 확인 중 주소에 글자를 넣었더니 `MethodArgumentTypeMismatchException`이 "처리 못 한 예외"로 저장됐다.
   오타나 봇 요청이 에러 로그에 섞이면 진짜 장애가 묻힌다 → 400으로 바꾸고 에러 로그에는 남기지 않는다 (`ErrorLogTest`).

## 전후 비교

| 상황 | 처음 | 지금 |
|---|---|---|
| 남의 차례 문서 승인 시도 (업무 예외) | 기록 0건 (롤백) | 실패 1건 + 이유 |
| 두 탭 동시 승인, 늦은 쪽 커밋 충돌 | 성공 2건 (거짓) | 성공 1건, 실패 1건 |
| `/requests/abc` | 500, 에러 로그 1건 | 400, 에러 로그 0건 |

## 배운 점

- AOP로 "메서드 앞뒤"에 끼우는 일은 트랜잭션 경계와 어디가 겹치는지를 먼저 정해야 한다. 어드바이스 순서는 기본값에 맡기지 않는다.
- 기록·알림처럼 업무와 운명이 달라야 하는 저장은 REQUIRES_NEW. 반대로 "커밋됐을 때만" 해야 하는 일(성공 기록, 메일 발송)은 afterCommit/afterCompletion.
- 스프링 AOP는 프록시 기반이라 `this.method()`에는 걸리지 않는다. `@Transactional`도 같다.
