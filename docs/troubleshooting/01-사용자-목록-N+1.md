# 사용자 목록을 열 때 쿼리가 11번 나가는 문제 (N+1)

- 단계: 3단계 / 관련 PR: #3
- 키워드: JPA, N+1, 지연 로딩(LAZY), fetch join, QueryDSL, Hibernate Statistics

## 상황

관리자 화면의 사용자 목록(`/admin/members`)은 한 줄마다 **부서 이름**과 **직급 이름**을 같이 보여 줍니다.
처음에는 `memberRepository.findAll()`로 사용자를 가져오고, 화면에서 `member.department.name`,
`member.position.name`을 읽게 만들었습니다.

## 증상

화면은 잘 나오는데, 콘솔(`org.hibernate.SQL: debug`)에 select 문이 줄줄이 찍혔습니다.

```sql
select ... from member m1_0                          -- 사용자 10명 (1번)
select ... from department d1_0 where d1_0.id=?      -- 팀1
select ... from position p1_0 where p1_0.id=?        -- 직급1
select ... from department d1_0 where d1_0.id=?      -- 팀2
select ... from position p1_0 where p1_0.id=?        -- 직급2
...                                                  -- (부서 5번 + 직급 5번)
```

`MemberRepositoryTest`로 쿼리 수를 세어 보니 다음과 같았습니다.

```
[N+1] 사용자 10명 목록 쿼리 수 = 11
```

사용자가 1,000명이고 부서·직급이 다양하면 수백 번이 될 수 있습니다.

## 원인

`Member`의 부서와 직급은 `@ManyToOne(fetch = FetchType.LAZY)`입니다.
LAZY는 "진짜 필요할 때 가져온다"는 뜻이라, `findAll()`은 사용자 표만 읽고 부서·직급 자리에는 **가짜 객체(프록시)**를 넣어 둡니다.
화면에서 `department.name`을 읽는 순간 그 부서를 가져오는 쿼리가 따로 나갑니다.

- 사용자 목록 1번 + 처음 보는 부서마다 1번(5) + 처음 보는 직급마다 1번(5) = **11번**
- 같은 부서는 1차 캐시(영속성 컨텍스트)에 이미 있으니 다시 가져오지 않습니다. 그래서 10 × 2 = 20이 아니라 11입니다.

> EAGER로 바꾸면 해결될 것 같지만, `findAll()` 같은 JPQL은 EAGER여도 사용자부터 읽고 나서 부서를 따로 읽기 때문에 N+1이 그대로 생깁니다.
> 그리고 부서가 필요 없는 화면에서도 항상 같이 읽게 되므로 기본은 LAZY로 두고, 필요한 곳에서만 같이 가져오는 것이 원칙입니다.

## 해결

목록 조회를 QueryDSL로 바꾸고 **fetch join**으로 부서·직급을 한 번에 가져왔습니다.

```java
// MemberRepositoryImpl.search()
return queryFactory
        .selectFrom(member)
        .join(member.department, department).fetchJoin()   // 부서를 같이 가져온다
        .join(member.position, position).fetchJoin()       // 직급도 같이 가져온다
        .where(keywordContains(cond.keyword()), departmentEq(cond.departmentId()), roleEq(cond.role()))
        .orderBy(department.code.asc(), position.rankOrder.desc(), member.name.asc())
        .fetch();
```

로그인할 때 쓰는 조회도 부서 이름을 화면 상단에 보여 주므로 같은 방식으로 바꿨습니다.

```java
@Query("select m from Member m join fetch m.department where m.loginId = :loginId")
Optional<Member> findByLoginIdWithDepartment(@Param("loginId") String loginId);
```

## 전후 비교

`MemberRepositoryTest` (사용자 10명, 팀 5곳, 직급 5개, H2)

| 방법 | 쿼리 수 |
|---|---|
| `findAll()` 후 부서·직급 이름 읽기 | **11** |
| `search()` (fetch join) | **1** |

쿼리 수는 Hibernate Statistics(`generate_statistics: true`)의 `getPrepareStatementCount()`로 셌고,
테스트에서 `assertThat(queries).isEqualTo(1)`로 고정해 두었기 때문에 누가 fetch join을 빼면 테스트가 깨집니다.

## 배운 점

- 목록 화면에서 연관된 엔티티의 값을 보여 준다면, 먼저 **SQL 로그에서 같은 모양의 select가 반복되는지** 본다.
- 기본은 LAZY, 목록처럼 같이 필요한 곳에서만 fetch join.
- 숫자로 남기려면 Hibernate Statistics로 쿼리 수를 세는 테스트를 만들어 둔다.
- 다음에 볼 것: fetch join은 **페이징과 같이 쓰면** 문제가 생길 수 있다 (컬렉션 fetch join + 페이징). 4단계에서 `default_batch_fetch_size`와 함께 다룬다.
