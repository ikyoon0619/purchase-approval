# 같은 품목을 동시에 입고하면 재고 수량이 어긋나는 문제 (Lost Update)

- 단계: 7단계 (발주·입고·재고) / 관련 PR: #7
- 키워드: Lost Update, 비관적 락, `PESSIMISTIC_WRITE`, `SELECT … FOR UPDATE`, 데드락, `innodb_lock_wait_timeout`

## 상황

BR-08: "입고 처리 때 재고를 늘리고 이력을 남긴다. 동시에 입고해도 수량이 어긋나면 안 된다."
처음 떠오르는 코드는 이렇다.

```java
Inventory inv = inventoryRepository.findByItemId(itemId);   // 1. 읽고
inv.increase(qty);                                         // 2. 메모리에서 더하고
// 3. 커밋할 때 변경 감지로 update inventory set quantity = ? where id = ?
```

## 증상 (`InventoryConcurrencyTest`)

```
트랜잭션 A (발주 1 입고 3개): 0개로 읽음 ─────────────────────── 0+3 = 3 저장, 커밋
트랜잭션 B (발주 2 입고 5개):          0개로 읽음 → 0+5 = 5 저장, 커밋
```

결과 재고 **3개** (기대 8개). 예외도 로그도 없이 B의 입고 5개가 사라졌다.
UPDATE가 `quantity = quantity + 3`이 아니라 `quantity = 3`(A가 메모리에서 계산한 값)으로 나가기 때문이다.

## 원인

변경 감지(dirty checking)는 "읽었을 때 값"을 기준으로 계산한 결과를 통째로 덮어쓴다.
두 트랜잭션이 같은 행을 읽은 뒤 각자 쓰면 나중에 쓴 쪽이 이긴다 (Lost Update).
`inventory`에는 `@Version`도 없어서 충돌을 알아챌 방법이 없었다.

## 선택지

| 방법 | 동작 | 이 화면에 맞나 |
|---|---|---|
| 낙관적 락 (`@Version`) | 나중 커밋을 실패시킴 | 입고는 충돌이 잦을 수 있고(같은 품목, 같은 날), 실패하면 다시 해야 함. 재고는 "실패"가 아니라 "차례대로 둘 다 반영"이 맞다 |
| 원자적 UPDATE (`set quantity = quantity + :n`) | DB가 더함 | 빠르지만 이력에 남길 "처리 후 수량"을 알려면 다시 읽어야 하고, 음수 검사도 SQL로 따로 |
| **비관적 락 (`SELECT … FOR UPDATE`)** | 먼저 온 트랜잭션이 끝날 때까지 뒤 트랜잭션이 기다림 | 둘 다 반영되고, 잠근 상태에서 읽은 수량으로 이력·음수 검사를 할 수 있다 → **선택** |

6단계 결재는 낙관적 락(충돌 드묾, 사람이 다시 판단)을, 7단계 재고는 비관적 락(충돌 잦음, 둘 다 반영)을 골랐다.

## 해결

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select v from Inventory v where v.item.id = :itemId")
Optional<Inventory> findByItemIdForUpdate(@Param("itemId") Long itemId);
```

```sql
select ... from inventory where item_id=? for update
```

재고를 바꾸는 메서드(`InventoryService.receive`, `ship`)는 모두 이 메서드로 읽는다: **잠그기 → 바꾸기 → 이력 기록 → 커밋(잠금 풀림)**.

### 함께 챙긴 것

1. **재고 행은 품목을 만들 때 같이 만든다.** "첫 입고 때 없으면 INSERT"로 하면 두 입고가 동시에 둘 다 INSERT 하다가 UNIQUE 위반이 난다. 잠글 행이 아직 없으면 FOR UPDATE도 소용없다. 이전 단계에서 만든 품목은 `InventoryInitializer`가 시작할 때 0개 행을 채운다.
2. **잠그는 순서를 고정한다 (데드락 방지).** 발주 A가 노트북→모니터, 발주 B가 모니터→노트북 순서로 잠그면 서로 상대 행을 기다리며 멈춘다. 입고할 때 품목 id 순으로 정렬해서 잠근다.
3. **오래 기다리지 않게 한다.** MySQL 기본 `innodb_lock_wait_timeout`은 50초. 접속 주소에 `sessionVariables=innodb_lock_wait_timeout=5`를 붙여 5초로 줄였고, 넘기면 `PessimisticLockingFailureException` → "잠시 후 다시 시도해 주세요".
   - 처음엔 JPA 힌트 `jakarta.persistence.lock.timeout=3000`을 붙였는데, 테스트 로그의 SQL에 `for update`만 있고 대기 시간은 어디에도 없었다. 찾아보니 Hibernate의 MySQL 방언도 0(NOWAIT) 말고는 SQL에 반영하지 않는다. 그래서 힌트를 지우고 DB 세션 설정으로 옮겼다.
4. **같은 발주서 이중 입고**는 `PurchaseOrder`에 `@Version`을 두어 나중 커밋이 실패하게 했다. 재고 증가도 같은 트랜잭션이라 함께 롤백된다.
5. 잠금 쿼리에 `join fetch`를 붙이지 않았다 (6단계에서 배운 것: 락은 같이 읽은 행에도 걸린다).

## 전후 비교

| 테스트 | 락 없이 | FOR UPDATE |
|---|---|---|
| A 읽기 → B(+5) 커밋 → A(+3) 커밋 | 3개 (5개 유실) | (같은 스레드에서 B가 A의 잠금을 기다려 재현 불가 → 아래 스레드 테스트로 확인) |
| 스레드 10개가 동시에 +1 | (측정 안 함: 타이밍에 따라 결과가 달라서 위의 순서 고정 테스트로 재현) | 항상 10개, 각 트랜잭션이 본 처리 후 수량이 1~10으로 겹치지 않음, 이력 10건 |

## 배운 점

- 변경 감지는 "계산된 값"으로 덮어쓴다. 같은 행을 여러 요청이 동시에 더하고 빼는 곳(재고, 포인트, 좌석)은 락이나 원자적 UPDATE가 필요하다.
- 낙관적/비관적은 우열이 아니라 "충돌이 났을 때 어떻게 되길 원하나"로 고른다. 실패시킬까(결재), 줄 세울까(재고).
- 비관적 락을 쓰면 데드락과 대기 시간도 같이 설계해야 한다: 잠그는 순서 고정, 대기 한도.
- 설정이 정말 먹혔는지는 실행된 SQL로 확인한다.
